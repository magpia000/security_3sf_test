# 개발 규칙: oss-vuln-fix-finder

- 위치: 3-File System의 세 번째 파일 (`prd` → `tasks` → `rules`)
- 함께 읽을 파일: `분석_설계/prd-oss-vuln-fix-finder.md`, `분석_설계/tasks-oss-vuln-fix-finder.md`
- 기반 규칙: `ai-dev-tasks/process-task-list.md` (이 프로젝트에 맞게 확장. 둘이 다르면 이 파일을 따른다)
- 읽는 사람: 태스크를 구현하는 AI 개발자와 주니어 개발자

구현을 시작하기 전과 매 하위 태스크를 시작할 때 이 파일을 다시 읽는다.

---

## 1. 문서 우선순위

1. 사용자의 현재 지시
2. 이 파일(`rules.md`)
3. PRD — 무엇을 만들지의 기준
4. tasks — 어떤 순서로 만들지의 기준

PRD와 tasks가 서로 맞지 않으면 구현하지 말고 어느 쪽을 고칠지 사용자에게 묻는다.

## 2. 작업 진행 절차

### 2.1 한 번에 하위 태스크 하나
- 하위 태스크(예: 1.1) 하나를 끝내면 **멈추고** 사용자에게 다음 진행 여부를 묻는다. 사용자가 `yes` 또는 `y`라고 답하기 전에는 다음 하위 태스크를 시작하지 않는다.
- 하나의 하위 태스크 범위를 넘는 코드를 미리 작성하지 않는다.

### 2.2 하위 태스크 완료 시
1. 해당 하위 태스크와 관련된 테스트를 실행한다: `uv run pytest tests/<관련 파일> -q`
2. tasks 파일에서 `- [ ]`를 `- [x]`로 바꾼다.
3. 새로 만들거나 고친 파일을 tasks 파일의 `Relevant Files`에 반영한다.
4. 작업 중 새로 필요한 태스크가 생기면 tasks 파일에 추가하고 사용자에게 알린다.
5. 사용자에게 보고한다: 한 일(2~3줄), 바뀐 파일, 테스트 결과, 다음 하위 태스크 번호.

### 2.3 상위 태스크 완료 시 (하위가 모두 `[x]`)
1. 전체 테스트를 실행한다: `uv run pytest -q`
2. 전부 통과해야만 다음으로 간다. 실패하면 고친 뒤 다시 실행한다.
3. 임시 파일과 임시 코드(디버그 출력, 주석 처리된 코드)를 지운다.
4. tasks 파일의 해당 상위 태스크 바로 아래에 완료 기록을 한 줄 남긴다.
   - 형식: `  > 완료 YYYY-MM-DD HH:MM — <요약> — 파일: <주요 파일> — 테스트: <통과 수>/<전체 수>`
5. 상위 태스크를 `[x]`로 바꾼다.

### 2.4 git
- 이 프로젝트는 git을 쓰지 않는다. `git` 명령을 실행하지 않고, 커밋·브랜치 태스크를 만들지 않는다.

## 3. 개발 환경과 명령

| 목적 | 명령 |
|---|---|
| 의존성 추가 | `uv add <패키지>` (개발용은 `uv add --dev pytest`) |
| 테스트 | `uv run pytest -q` |
| 수집 | `uv run python -m oss_vuln_fix_finder collect --input data/오픈소스_컴포넌트목록.xlsx --bundle bundles/` |
| 분석 | `uv run python -m oss_vuln_fix_finder scan --input data/오픈소스_컴포넌트목록.xlsx --bundle bundles/<묶음>.zip --output output/` |

- OS는 Windows, Python은 3.12이다. `pip install`을 직접 쓰지 않는다. 가상환경은 기존 `.venv`를 쓴다.
- 경로는 `pathlib.Path`로 다루고, 경로 구분자(`\`, `/`)를 문자열로 이어 붙이지 않는다.
- 파일을 열 때는 항상 `encoding="utf-8"`을 명시한다(Windows 기본 인코딩은 cp949라 한글이 깨진다).
- 파일명·폴더명에 한글이 있으므로(`data/오픈소스_…xlsx`) 경로를 하드코딩하지 말고 CLI 인자로 받는다.

## 4. 코드 규칙

### 4.1 구조
- 패키지 구조는 PRD 7장을 따른다. 새 모듈이 필요하면 tasks의 `Relevant Files`에 먼저 적는다.
- 모듈 역할을 섞지 않는다.
  - `collect/`: 네트워크 요청만 한다. 판정 로직을 넣지 않는다. 진행 상황은 `logging`(또는 콜백)으로 넘기고 직접 출력하지 않는다.
  - `bundle.py`: 묶음 zip 쓰기·읽기만 한다. scan도 쓰므로 `collect/` 밖에 두고 `requests`를 import하지 않는다.
  - `analyze/`: 순수 함수로 판정만 한다. 네트워크·파일 입출력을 하지 않는다.
  - `versions/`: 버전 문자열 비교·브랜치·사전배포판 판정만 한다.
  - `io_excel.py`: 엑셀 읽기·쓰기만 한다.

### 4.2 작성 방식
- 식별자(변수·함수·클래스)는 영어, 주석·docstring·콘솔 메시지·로그 메시지는 한국어로 쓴다.
- 모든 공개 함수에 타입 힌트와 docstring을 단다(형식은 4.5).
- 데이터 구조는 `dataclass`로 정의한다(예: `Component`, `Vulnerability`, `Remediation`). 딕셔너리를 여러 함수에 걸쳐 넘기지 않는다.
- 함수는 한 가지 일만 하고 50줄을 넘기지 않는 것을 목표로 한다.
- 콘솔 출력은 CLI 진입점(`__main__.py`)에서만 한다. 나머지 모듈은 `logging`을 쓴다.
- 예외를 삼키지 않는다. 컴포넌트 단위 실패는 잡아서 기록하고 다음 컴포넌트로 넘어가되(PRD 4.2-11), 원인 메시지를 남긴다.

### 4.3 데이터 처리
- 입력 엑셀의 버전은 **항상 문자열**로 읽는다(`dtype=str`). 숫자 변환이 일어나면 버그다.
- 컴포넌트 식별자(Maven 좌표, CPE)는 `config/component_map.yaml`에만 둔다. 코드에 하드코딩하지 않는다.
- 버전 비교는 `versions/`의 함수만 쓴다. `str` 비교나 `packaging.version`으로 대신하지 않는다.
- 조치 버전 판정은 PRD 4.3의 A안(현재 집합 C-해결 / 전체 집합 무취약)을 그대로 따른다. 규칙을 바꿔야 할 것 같으면 구현하지 말고 묻는다.
- `data/` 폴더의 원본 엑셀은 읽기만 하고 수정하지 않는다. 결과는 `output/`에만 쓴다.

### 4.4 가독성과 유지보수성

코드는 처음 보는 주니어 개발자가 한 번 읽고 이해하고 고칠 수 있어야 한다.

- **이름으로 의도를 드러낸다.** `v`, `tmp`, `data2` 같은 이름 대신 `current_version`, `affected_cves`, `candidate_versions`처럼 무엇인지 알 수 있게 쓴다. 불리언은 `is_`, `has_`로 시작한다(예: `is_prerelease`).
- **PRD 용어를 코드 용어와 맞춘다.** PRD의 현재 집합 C·전체 집합 K·C-해결·무취약은 각각 `current_cves`, `all_cves`, `resolves_current`, `is_clean`으로 통일하고 다른 이름을 섞지 않는다.
- **중첩을 얕게 유지한다.** 들여쓰기 3단계를 넘으면 조기 반환(early return)이나 보조 함수로 나눈다.
- **매직 값을 쓰지 않는다.** 요청 간격(6초), 재시도 횟수(5회), 시트명, 열 이름, 상태 문자열(`UNMAPPED` 등)은 모듈 상단 상수나 `Enum`으로 한곳에 정의한다.
- **중복을 만들지 않는다.** 같은 로직이 두 번 나오면 함수로 뽑는다. 단, 억지로 일반화하지 않고 실제로 두 곳 이상에서 쓸 때만 뽑는다.
- **변경이 한곳에서 끝나게 한다.** 컴포넌트 추가는 매핑 파일, 버전 규칙 추가는 `versions/` 모듈 추가, 출력 열 변경은 `io_excel.py`의 열 정의만 고치면 되도록 구조를 유지한다.
- **부수 효과를 드러낸다.** 파일을 쓰거나 상태를 바꾸는 함수는 이름에 동사로 드러낸다(예: `write_bundle`, `save_report`). 계산 함수는 입력 인자를 수정하지 않고 새 값을 반환한다.
- **포맷을 일관되게 한다.** PEP 8을 따르고, 한 줄은 100자 이내로 쓴다. import는 표준 라이브러리 → 외부 패키지 → 프로젝트 모듈 순서로 묶는다.

### 4.5 주석 작성

주석은 코드가 **무엇을** 하는지가 아니라 **왜** 그렇게 하는지를 설명한다.

- **모듈 docstring**: 파일 맨 위에 모듈의 역할을 1~3줄로 적는다.
- **함수·클래스 docstring**: 공개 함수와 클래스에는 Google 스타일 docstring을 단다. 한 줄 요약 다음에 `Args`, `Returns`, `Raises`를 필요한 만큼 적는다.

```python
def pick_nearest_fix(current: str, candidates: list[str], ...) -> Remediation:
    """해결 가까운 버전을 PRD 4.3-19의 1~4단계 순서로 고른다.

    Args:
        current: 입력 엑셀의 현재 버전(정규화 후).
        candidates: 현재 버전보다 높은 안정 버전 목록.

    Returns:
        고른 버전과 비고 문구를 담은 Remediation.
    """
```

- **근거를 남기는 주석**: PRD 규칙을 구현한 곳에는 해당 번호를 적는다(예: `# PRD 4.3-19-2: 동일 브랜치 최종 버전으로 대체`). 외부 데이터 형식에 기댄 코드에는 그 사실을 적는다(예: `# NVD는 configurations가 비어 있는 CVE도 반환한다`).
- **비직관적인 처리에는 반드시 주석을 단다.** 버전 문자열 파싱 규칙(`0.9.8zh`의 `z` 이중 접미사 등), 요청 간격·재시도 값의 이유, 예외를 잡고 계속 진행하는 이유가 해당한다.
- **달지 않는 주석**: 코드를 그대로 읽어 주는 주석(`# i를 1 증가`), 주석 처리된 옛 코드, 작성자·날짜 기록은 남기지 않는다.
- **주석을 코드와 함께 고친다.** 코드를 바꾸면 그 위의 주석과 docstring이 여전히 맞는지 확인한다. 틀린 주석은 주석이 없는 것보다 나쁘다.
- **TODO는 태스크 번호와 함께 쓴다.** 형식은 `# TODO(3.2): ...`이며, 상위 태스크를 완료하기 전에 모두 해소하거나 tasks 파일에 새 태스크로 옮긴다.

## 5. 네트워크와 외부 API 규칙

- 네트워크 요청은 `collect/` 안에서만 한다. `analyze/`, `versions/`, `bundle.py`, `io_excel.py`, scan 경로에서는 `requests`를 import하지 않고, `collect/`를 import하지도 않는다.
- scan의 네트워크 차단은 테스트로 보장한다(소켓 연결을 막은 상태에서 scan 통합 테스트가 통과해야 한다).
- NVD는 API 키 없이 호출한다. 요청 간격은 최소 6초이고, 403·429·5xx에는 지수 백오프로 최대 5회 재시도한다.
- 모든 요청에 식별 가능한 `User-Agent`(예: `oss-vuln-fix-finder/0.1`)를 넣는다.
- 토큰·키·개인정보를 코드나 묶음 파일에 저장하지 않는다.

## 6. 테스트 규칙

- 테스트는 `tests/` 아래에 모듈 구조를 따라 둔다(예: `oss_vuln_fix_finder/versions/openssl.py` → `tests/versions/test_openssl.py`).
- **단위 테스트에서 실제 네트워크를 호출하지 않는다.** API 응답은 `tests/fixtures/`에 저장한 JSON·XML 샘플로 대신한다.
- 버전 비교 테스트는 `pytest.mark.parametrize`로 표 형태로 쓰고, PRD 4.4 표의 순서 예를 모두 넣는다.
- 조치 버전 테스트는 PRD 4.3-23-1을 따른다(19번 1~4단계, LTS 비고, OpenSSL 0.9.8h 회귀).
- 버그를 고칠 때는 그 버그를 재현하는 테스트를 먼저 쓰고, 실패를 확인한 뒤 코드를 고친다.
- 테스트를 지우거나 `skip`·`xfail`로 바꿔서 통과시키지 않는다. 필요하면 사용자에게 이유를 말하고 승인을 받는다.
- 실제 API를 호출하는 확인은 태스크 6.0에서만 하고, 결과는 테스트가 아니라 검증 기록으로 남긴다.

## 7. 멈추고 물어야 하는 경우

다음 상황에서는 추측으로 진행하지 말고 사용자에게 묻는다.

- PRD 9장 미결 질문(OQ-1~6)에 걸리는 결정이 필요할 때
- PRD에 없는 기능이나 동작이 필요해 보일 때(범위 확장)
- 새 외부 패키지를 추가하려 할 때(PRD 7장 목록 외)
- 실제 API 응답 구조가 PRD의 가정과 다를 때
- 같은 테스트 실패를 두 번 고쳐도 해결되지 않을 때

질문할 때는 선택지를 번호·문자(예: `1A`, `1B`)로 제시하고, 권장안을 하나 표시한다.

## 8. 금지 사항

- git 명령 실행
- 사용자 승인 없이 다음 하위 태스크로 넘어가기
- PRD에 없는 기능 추가, PRD 5장(비목표) 항목 구현
- `data/` 원본 파일 수정
- 컴포넌트 식별자·CPE vendor를 근거 없이 확정하기(첫 수집 결과로 확인한다)
- 테스트를 지우거나 건너뛰게 해서 통과시키기
- scan 경로에서 네트워크 요청

## 9. 완료 정의 (Definition of Done)

하위 태스크는 다음을 모두 만족해야 완료다.

- [ ] 해당 범위의 코드가 4장 규칙을 지킨다(4.4 가독성·유지보수성, 4.5 주석 포함)
- [ ] 관련 테스트가 있고 통과한다
- [ ] tasks 파일의 체크박스와 `Relevant Files`가 갱신되었다
- [ ] 임시 코드·디버그 출력이 남아 있지 않다

전체 기능은 PRD 8장 성공 지표 7개를 모두 만족하면 완료다.
