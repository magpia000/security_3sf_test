## 1. 개요 (Introduction/Overview)

보안담당자는 조직이 사용하는 오픈소스 컴포넌트 목록(엑셀)을 받으면, 컴포넌트마다 NVD·OSV 웹사이트를 일일이 검색해 취약점을 찾고, 어느 버전으로 올려야 안전한지 손으로 판단해 왔다. 버전 표기 방식이 컴포넌트마다 달라(`0.9.8h`, `8b`, `llvmorg-9.0.1-rc3`) 판단 실수도 잦다.

이 도구는 컴포넌트 목록 엑셀을 입력받아 다음을 자동으로 수행하는 **Python CLI 프로그램**이다.

1. 컴포넌트·버전별로 알려진 보안취약점(CVE)을 찾는다.
2. 취약점을 해결하는 업그레이드 버전 두 가지를 제시한다(정확한 판정 규칙은 4.3절).
   - **해결 가까운 버전**: 현재 버전에서 가장 적게 올리면서 현재 버전의 취약점이 해결되는 버전
   - **최신 버전**: 알려진 취약점이 없는 최신 안정 버전
3. 결과를 엑셀 보고서로 저장한다.

실행 PC가 **폐쇄망**일 수 있으므로, 인터넷 PC에서 데이터를 수집하는 `collect` 단계와 폐쇄망 PC에서 분석하는 `scan` 단계로 나눈다.

## 2. 목표 (Goals)

| ID | 목표 | 측정 방법 |
|---|---|---|
| G1 | 입력 목록의 모든 컴포넌트에 대해 취약점 목록과 조치 버전 2종을 한 번의 실행으로 산출한다 | 입력 13행 전부가 출력에 1행 이상 존재 |
| G2 | 폐쇄망 PC에서 인터넷 연결 없이 분석을 끝낸다 | `scan` 실행 중 네트워크 호출 0건 |
| G3 | 같은 수집 묶음(bundle)으로 다시 실행하면 같은 결과가 나온다 | 두 번 실행한 출력 엑셀이 `조회일시` 열을 빼고 동일 |
| G4 | 사람이 검증할 수 있도록 판단 근거를 남긴다 | 모든 취약점 행에 근거 소스·영향 범위 기재 |

## 3. 사용자 스토리 (User Stories)

주 사용자는 **보안담당자**이며, 정기 보안 점검 때 CLI를 직접 실행한다.

- **US-1** 보안담당자로서, 인터넷 PC에서 컴포넌트 목록 엑셀을 넣고 명령 한 줄(`collect`)로 필요한 취약점 데이터를 모두 내려받고 싶다. 그래야 폐쇄망으로 옮길 파일을 한 번에 준비할 수 있다.
- **US-2** 보안담당자로서, 수집한 묶음 파일을 폐쇄망 PC에 옮긴 뒤 명령 한 줄(`scan`)로 취약점 보고서 엑셀을 만들고 싶다. 그래야 폐쇄망에서도 점검을 끝낼 수 있다.
- **US-3** 보안담당자로서, 취약점이 발견된 컴포넌트마다 "최소한으로 올릴 버전"과 "최신 버전"을 함께 보고 싶다. 그래야 개발팀에 현실적인 조치안(호환성 부담이 적은 쪽)과 장기 조치안을 같이 제시할 수 있다.
- **US-4** 보안담당자로서, 같은 브랜치에서는 완전히 해결할 수 없는 경우(지원 종료 등) 그 사실과 남는 취약점을 알고 싶다. 그래야 브랜치 변경이 필요하다고 판단할 수 있다.
- **US-5** 보안담당자로서, 도구가 인식하지 못한 컴포넌트가 있으면 결과에서 바로 알고 싶다. 그래야 누락 없이 수작업으로 보완할 수 있다.

## 4. 기능 요구사항 (Functional Requirements)

### 4.1 공통

1. 시스템은 CLI 명령 두 개(`collect`, `scan`)를 제공해야 한다.
   - `uv run python -m oss_vuln_fix_finder collect --input data/오픈소스_컴포넌트목록.xlsx --bundle bundles/`
   - `uv run python -m oss_vuln_fix_finder scan --input data/오픈소스_컴포넌트목록.xlsx --bundle bundles/bundle_YYYYMMDD_HHMM.zip --output output/ [--include-disputed]`
2. 시스템은 입력 엑셀(`Sheet1`, 열: `No`, `오픈소스 컴포넌트명`, `컴포넌트 버전`)을 읽어야 하며, 모든 값을 **문자열**로 읽어야 한다(`1.7`이 `1.70`이 되거나 `8b`가 손상되면 안 된다). 헤더의 줄바꿈과 영문 병기는 무시하고 앞부분 한글 이름으로 열을 찾는다.
3. 시스템은 컴포넌트명을 표준 식별자로 바꾸는 매핑 파일 `config/component_map.yaml`을 사용해야 한다. 매핑 항목은 다음을 가진다.
   - `name`: 입력 엑셀의 컴포넌트명
   - `type`: `maven` 또는 `native`
   - `maven`: Maven 좌표(예: `com.google.code.gson:gson`) — `type: maven`일 때
   - `cpe`: CPE 접두어 목록(예: `cpe:2.3:a:openssl:openssl`) — 모든 유형에 선택적으로, `native`는 필수
   - `version_rule`: 버전 비교 규칙 이름(4.4 참조)
   - `version_prefix`: 입력 버전에서 떼어낼 접두사(예: LLVM의 `llvmorg-`)
   - `lts_branches`: LTS 브랜치 목록(예: OpenSSL `["3.0"]`) — 수작업 관리
4. 매핑 파일에 없는 컴포넌트는 처리를 멈추지 않고 결과에 `UNMAPPED`로 표시해야 한다.
4-1. 시스템은 입력을 검증해야 한다. 필수 열(`No`, 컴포넌트명, 버전)이 없으면 즉시 오류 메시지를 내고 종료한다. 컴포넌트명이나 버전이 빈 행은 처리하지 않고 결과에 `INVALID_INPUT`으로 표시한 뒤 나머지 행을 계속 처리한다.
5. 초기 매핑 파일에는 현재 입력 13건(11개 컴포넌트)을 모두 넣어야 한다. 초안은 `RFP/요구사항.md` 3.2절 표를 따른다.

### 4.2 collect (인터넷 PC)

6. 시스템은 입력 목록의 컴포넌트만 대상으로 데이터를 수집해야 한다(전체 DB 덤프를 받지 않는다).
7. 시스템은 다음 데이터를 수집해야 한다.

| 대상 | 데이터 | 소스 |
|---|---|---|
| `maven` 컴포넌트 | 패키지의 **전체** 취약점 목록과 영향 범위 | OSV.dev API (`/v1/query`, ecosystem `Maven`, **version 없이** 패키지명만으로 조회) — GitHub Advisory(GHSA) 데이터가 OSV에 포함되어 있으므로 GitHub를 직접 조회하지 않는다 |
| `maven` 컴포넌트 | 전체 릴리스 버전 목록 | Maven Central `maven-metadata.xml` |
| `native` 컴포넌트 | 제품의 **전체** 취약점 목록과 영향 범위 | NVD CVE API 2.0 (`virtualMatchString`에 **버전 없는** CPE 접두어) |
| `native` 컴포넌트 | 전체 릴리스 버전 목록 | NVD CPE API 2.0 (`cpeMatchString`) |
| `cpe`가 있는 `maven` 컴포넌트 | 교차 확인용 취약점 목록 | NVD CVE API 2.0 |
| OSV 결과의 CVE 별칭 | CVSS 점수·설명 보완 | NVD CVE API 2.0 (`cveId`) |

7-1. 취약점은 현재 버전에 해당하는 것만이 아니라 컴포넌트의 **전체** 취약점을 수집한다. 4.3의 조치 버전 판정이 후보 버전들의 취약 여부를 검사해야 하기 때문이다.
7-2. `native` 컴포넌트는 OSV로 교차 검증하지 않는다. C/C++ 라이브러리는 OSV에 패키지 생태계가 없어 Git 커밋 범위 위주로 제공되므로 릴리스 버전 판정에 쓰기 어렵다.
8. 시스템은 **NVD API 키 없이** 동작해야 한다. NVD 공개 요청 제한(30초당 5회)을 지키도록 요청 간격을 최소 6초로 두고, 응답 403/429/5xx에는 지수 백오프로 최대 5회 재시도해야 한다.
9. 시스템은 NVD 결과가 여러 페이지면(`totalResults` > `resultsPerPage`) 모든 페이지를 받아야 한다.
10. 시스템은 수집한 원본 응답(JSON/XML)을 가공하지 않고 묶음 파일 하나(`bundles/bundle_YYYYMMDD_HHMM.zip`)에 저장해야 한다. 묶음에는 `manifest.json`을 넣어야 한다.
    - 수집일시(KST), 도구 버전, 입력 파일명과 SHA-256, 컴포넌트별 수집 성공/실패, 소스별 요청 수
11. 수집 중 일부 컴포넌트가 실패해도 나머지는 계속 수집하고, 실패 내역을 `manifest.json`과 콘솔에 남겨야 한다.
12. 수집 진행 상황(현재 컴포넌트, 남은 수, 예상 대기 시간)을 콘솔에 표시해야 한다.

### 4.3 scan (폐쇄망 PC)

13. 시스템은 `scan` 중 **어떠한 네트워크 요청도 하지 않아야** 한다. 묶음 파일에 없는 데이터가 필요하면 해당 컴포넌트를 `UNCOLLECTED`로 표시한다.
14. 시스템은 입력 엑셀과 묶음의 `manifest.json`의 입력 파일 해시를 비교해, 다르면 경고를 출력하고 계속 진행해야 한다.
15. 시스템은 각 입력 행에 대해 그 버전이 영향 범위에 포함되는 취약점을 찾아야 한다.
    - NVD: `configurations`의 `cpeMatch` 중 `vulnerable: true` 항목의 `versionStartIncluding/Excluding`, `versionEndIncluding/Excluding`, 또는 CPE 문자열에 박힌 정확한 버전으로 판정한다.
    - OSV: `affected[].ranges[].events`(`introduced`, `fixed`, `last_affected`)와 `affected[].versions` 목록으로 판정한다.
    - 버전 포함 여부는 반드시 4.4의 비교 규칙으로 판정한다. 문자열 일치만으로 판정하면 안 된다.
16. 시스템은 여러 소스에서 나온 같은 취약점을 CVE ID 기준으로 하나로 합쳐야 한다. OSV/GHSA ID는 `aliases`의 CVE ID로 바꾸고, CVE가 없으면 원래 ID를 쓴다. `근거 소스` 열에 결과를 낸 모든 소스를 적는다.
17. 시스템은 NVD 상태가 `Rejected`인 CVE를 항상 제외해야 한다. 분쟁(disputed) CVE(NVD `cveTags`에 `disputed`가 있거나 설명이 `** DISPUTED **`로 시작)는 기본 제외하고, `--include-disputed` 옵션을 주면 포함한다.

#### 해결 판정 기준 (A안)

18. 컴포넌트마다 다음 두 취약점 집합을 만든다.
    - **K (전체 집합)**: 묶음에 있는 그 컴포넌트의 전체 취약점(17번 제외 규칙 적용 후)
    - **C (현재 집합)**: K 중 현재 버전이 영향 범위에 드는 취약점(15번 판정)
18-1. 후보 버전은 전체 릴리스 버전 중 현재 버전보다 높은 **안정 버전**이다. 사전 배포판(`rc`, `alpha`, `beta`, `M`, `SNAPSHOT` 등)은 후보에서 뺀다.
18-2. 후보 버전 v에 대해 두 가지를 판정한다.
    - **C-해결**: C의 어떤 취약점에도 영향받지 않는다.
    - **무취약**: K의 어떤 취약점에도 영향받지 않는다(C-해결 + v에서 새로 생긴 취약점도 없음).

19. **해결 가까운 버전**은 다음 순서로 고른다. 먼저 맞는 단계에서 멈춘다.
    1. 같은 브랜치(4.4)의 후보 중 **C-해결**인 가장 낮은 버전. 그 버전이 무취약이 아니면 비고에 `신규 취약점: CVE-…`를 적는다.
    2. 1이 없고 같은 브랜치에 후보가 있으면, 같은 브랜치의 **가장 높은 후보 버전**(브랜치 최종 버전)을 고르고 비고에 `동일 브랜치 최종 버전, 미해결: CVE-…`를 적는다. 이어서 3의 규칙으로 찾은 버전이 있으면 비고에 `브랜치 변경 시: X.Y.Z`를 덧붙인다.
    3. 같은 브랜치에 후보가 없으면(현재 버전이 브랜치 최종 버전), 다른 브랜치의 후보 중 **무취약**인 가장 낮은 버전을 고르고 비고에 `브랜치 변경`을 적는다.
    4. 그래도 없으면 `해결 버전 없음`을 적는다.

20. **최신 버전**은 후보와 현재 버전을 포함한 전체 안정 버전 중 **무취약**인 가장 높은 버전이다.
    - 무취약 버전이 하나도 없으면 가장 높은 안정 버전을 적고 비고에 `최신 버전에도 미해결: CVE-…`를 적는다.
    - `lts_branches`가 설정되어 있고 고른 최신 버전이 LTS 브랜치에 속하지 않으면, LTS 브랜치들 중 무취약인 가장 높은 버전을 비고에 `LTS: X.Y.Z`로 적는다.

21. C가 비어 있는(현재 버전에 취약점이 없는) 컴포넌트는 `해결 가까운 버전`에 `-`를, `최신 버전`에 20번의 결과를 적는다.

21-1. 위 규칙의 기대 결과 예(원본 요구사항 예시): OpenSSL `0.9.8h` → 해결 가까운 버전은 0.9.8 브랜치 안에서 고른다. 0.9.8 브랜치로 모두 해결되지 않으면 19-2에 따라 `0.9.8zh` + 미해결 CVE 비고 + `브랜치 변경 시:` 비고가 된다. 최신 버전은 무취약인 최신 안정 버전 + LTS 비고이다.

### 4.4 버전 비교 규칙

22. 시스템은 다음 비교 규칙을 제공해야 하며, 컴포넌트마다 매핑 파일의 `version_rule`로 고른다.

| 규칙 | 대상 | 순서 예 | 브랜치 정의 |
|---|---|---|---|
| `maven` | Maven 컴포넌트 | `1.4.1` < `1.10` < `1.21` | 앞 두 자리(`1.4`) |
| `openssl` | OpenSSL | `0.9.8h` < `0.9.8za` < `0.9.8zh` < `1.0.0` < `1.0.2u` < `1.1.1w` < `3.0.8` | 3.0 미만: 문자 접미사를 뗀 숫자부(`0.9.8`, `1.0.2`, `1.1.1`), 3.0 이상: 앞 두 자리(`3.0`, `3.5`) |
| `letter_suffix` | libjpeg | `8` < `8a` < `8b` < `8d` < `9` < `9a` | 숫자부(`8`) |
| `semver_like` | GCC, LLVM, SQLite, zlib | `9.0.1-rc3` < `9.0.1` < `10.0.0`, `1.2.5` < `1.2.11` < `1.2.13` | GCC·LLVM: 첫 자리(`4`), SQLite·zlib: 앞 두 자리(`3.7`, `1.2`) |

23. 버전 비교 함수와 브랜치 함수는 각각 단위 테스트를 가져야 한다. 위 표의 순서 예를 모두 테스트 케이스로 넣는다.
23-1. 범위 판정(15번), CVE 병합(16·17번), 조치 버전 선택(18~21번)도 단위 테스트를 가져야 한다. 조치 버전 테스트에는 19번의 1~4단계와 20번의 LTS 비고가 각각 한 번 이상 나오는 가상 데이터와, OpenSSL 0.9.8h 회귀 테스트(21-1)를 넣는다.

### 4.5 출력

24. 시스템은 `output/오픈소스_컴포넌트별 취약점목록_YYYYMMDD_HHMM.xlsx`를 만들어야 한다. 앞 5개 열은 템플릿 `data/오픈소스_컴포넌트별 취약점목록.xlsx`와 같은 이름·순서를 유지한다.

| # | 열 이름 | 내용 |
|---|---|---|
| 1 | No | 입력 그대로 |
| 2 | 오픈소스 컴포넌트명 (Component name) | 입력 그대로 |
| 3 | 컴포넌트 버전 (Component version name) | 입력 그대로 |
| 4 | 보안취약점 ID (Vulnerability id) | CVE ID(없으면 OSV/GHSA ID). 행에 취약점이 없으면 `취약점 없음` / `UNMAPPED` / `UNCOLLECTED` / `INVALID_INPUT` |
| 5 | 보안취약점 설명 (Description) | 영문 원문 |
| 6 | CVSS 점수 | v3.1 → v3.0 → v4.0 → v2 순으로 처음 있는 것 |
| 7 | 심각도 | CRITICAL / HIGH / MEDIUM / LOW (6열과 같은 버전의 값) |
| 8 | 영향 버전 범위 | 예: `>=0.9.8, <0.9.8za` |
| 9 | 해결 가까운 버전 | 4.3-19, 21 |
| 10 | 최신 버전 | 4.3-20 |
| 11 | 비고 | 4.3-19·20의 비고 문구를 `; `로 이어 적는다 |
| 12 | 근거 소스 | `NVD; OSV` |
| 13 | 조회일시 | 묶음의 수집일시 |

25. 행 단위는 **CVE 1건당 1행**이다. 조치 버전(9, 10열)은 컴포넌트 단위 값이므로 같은 입력 행의 모든 CVE 행에 같게 적는다.
26. 행 정렬은 입력 `No` 오름차순, 그 안에서 CVSS 점수 내림차순이다.
27. 시스템은 실행 요약(입력 행 수, 취약점 발견 행 수, 총 CVE 수, 심각도별 수, UNMAPPED/UNCOLLECTED/INVALID_INPUT 수)을 콘솔에 출력해야 한다.
28. 시스템은 실행 로그를 `logs/` 아래 JSONL로 남겨야 한다(컴포넌트별 판정 건수, 오류).

## 6. 설계 고려사항 (Design Considerations)

- **실행 흐름**

```
[인터넷 PC]  입력 엑셀 → collect → bundles/bundle_YYYYMMDD_HHMM.zip
                                              │ (USB 등으로 반입)
[폐쇄망 PC]  입력 엑셀 + bundle.zip → scan → output/…xlsx, logs/…jsonl
```

- **엑셀 서식**: 헤더 굵게·고정(freeze), 열 너비 자동 조정, 설명 열 줄바꿈. 심각도 열에 색을 칠한다(CRITICAL 진한 빨강, HIGH 빨강, MEDIUM 주황, LOW 노랑). 같은 입력 행의 1~3열은 셀 병합하지 않는다(필터·정렬을 위해).
- **콘솔 메시지**는 한국어로 출력한다. collect의 진행 표시(4.2-12)는 수집 모듈이 직접 출력하지 않고 logging(또는 콜백)으로 CLI에 넘겨 CLI가 출력한다.

## 7. 기술 고려사항 (Technical Considerations)

- **환경**: Windows, Python 3.12, uv(`pyproject.toml` 기존 파일 사용). git은 사용하지 않는다.
- **의존성**: pandas(기존), openpyxl, requests, PyYAML, pytest. 버전 비교는 외부 패키지 없이 직접 구현한다(`packaging`은 Maven·OpenSSL 규칙을 처리하지 못한다).
- **폐쇄망 반입**: 폐쇄망 PC에도 같은 Python 패키지가 필요하다. `uv` 오프라인 설치용 wheel 묶음 준비 절차를 README에 적는다.
- **권장 패키지 구조**

```
oss_vuln_fix_finder/
  __main__.py        # CLI (argparse): collect, scan
  io_excel.py        # 입력 읽기, 출력 쓰기
  mapping.py         # component_map.yaml 로드
  bundle.py          # 묶음 zip 쓰기(collect)·읽기(scan) — 네트워크 없음, collect/ 밖에 둔다
  collect/           # nvd.py, osv.py, maven.py — 네트워크 요청은 여기서만
  analyze/           # matcher.py(범위 판정), merger.py(CVE 병합), remediation.py(조치 버전)
  versions/          # maven.py, openssl.py, letter_suffix.py, semver_like.py
config/component_map.yaml
tests/
```

- **NVD 요청량 추정**: 키 없이 요청 간격 6초이다. 네이티브 6종 × (CVE 조회 1~5페이지 + CPE 조회 1~2페이지)에 OSV 결과의 CVE 별칭을 한 건씩 보완 조회(4.2-7 마지막 행, Maven 5종 합계 수십 건 예상)하면 약 60~120회, 즉 6~12분이 걸린다. 수집은 1회성이므로 허용하되, 같은 CVE를 두 번 조회하지 않도록 수집 중 중복을 제거한다. 실제 수치는 첫 수집에서 확인한다.
- **성능**: scan은 13개 컴포넌트 기준 30초 이내에 끝나야 한다.
- **확장성**: 컴포넌트 추가는 매핑 파일 항목 추가만으로 가능해야 하고, 새 버전 규칙이 필요할 때만 `versions/`에 모듈을 추가한다.
- **LTS 목록**: `lts_branches`는 수작업으로 관리한다. OpenSSL 초기값은 `["3.0", "3.5"]`로 두되 공식 릴리스 정책으로 확인한다(OQ-6).
- **CPE vendor 확인 필요**: libjpeg(`ijg:libjpeg` 외 다른 vendor 표기 가능), LLVM(`llvm:llvm`), zlib(`zlib:zlib`, `gnu:zlib` 병행)은 첫 수집 결과로 확인한 뒤 매핑을 확정한다.
- **NVD CPE 버전 목록의 한계**: NVD에 등록된 버전만 나오므로 최신 릴리스가 늦게 반영되거나 일부 버전이 빠질 수 있다. 이번 범위에서는 감수하고, 비고에 `버전 목록 출처: NVD CPE`를 적는다.

## 8. 성공 지표 (Success Metrics)

1. 현재 입력 13행 전부가 출력에 1행 이상 나오고, `UNMAPPED`는 0건이다.
2. 취약점이 발견된 모든 행에 `해결 가까운 버전`과 `최신 버전`이 채워지거나, 채우지 못한 사유가 비고에 있다.
3. OpenSSL `0.9.8h`의 결과가 4.3-21-1의 기대 결과와 일치한다(해결 가까운 버전은 0.9.8 브랜치 버전, 예상 `0.9.8zh`).
4. 표본 3개 컴포넌트(OpenSSL 0.9.8h, zlib 1.2.5, gson 1.7)의 결과를 NVD/OSV 웹사이트 조회와 손으로 대조했을 때 누락·오탐이 없다.
5. 같은 묶음으로 `scan`을 두 번 실행한 결과가 `조회일시` 열을 빼고 동일하다.
6. `scan` 실행 중 네트워크를 끈 상태에서도 정상 종료한다.
7. `pytest` 전체가 통과한다.
8. `scan`이 13개 컴포넌트 기준 30초 이내에 끝난다.
