# 오픈소스 컴포넌트 보안취약점 식별 및 조치 버전 추천 도구 — 요구사항 명세

- 문서 버전: v0.2 (2026-10-10, PRD 검토 결과 동기화)
- 원본: `RFP/요구사항.txt`
- 용도: 3-File System의 입력 문서로 사용한다. 산출물은 `분석_설계/`의 `prd-oss-vuln-fix-finder.md`, `tasks-oss-vuln-fix-finder.md`, `rules.md`이다.
- 우선순위: 세부 규칙은 PRD가 기준이다. 이 문서는 PRD와 같은 결정을 요약해 유지한다.
- 표기: 결정이 필요한 항목은 `[확인 필요]`로 표시한다.

---

## 1. 배경 및 목적

조직이 사용하는 오픈소스 컴포넌트 목록(엑셀)을 입력받아, 컴포넌트·버전별로 알려진 보안취약점(CVE 등)을 찾고, 각 컴포넌트를 조치하기 위한 업그레이드 버전을 두 가지 기준(가까운 해결 버전, 최신 해결 버전)으로 제시하는 도구를 만든다.

이번 범위는 위 도구의 구현까지이다.

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| 컴포넌트 | 입력 엑셀의 `오픈소스 컴포넌트명` (예: OpenSSL) |
| 소스 버전 | 입력 엑셀에 기재된 현재 사용 버전 (예: 0.9.8h) |
| 취약점 | CVE ID 또는 그에 대응하는 Advisory ID(GHSA, OSV ID)로 식별되는 공개 보안취약점 |
| 영향 범위 | 취약점 DB가 제공하는 affected version range (introduced ~ fixed / lastAffected) |
| 해결 가까운 버전 | 소스 버전보다 높은 안정 버전 중, 소스 버전에 영향을 주는 취약점(현재 집합)을 모두 해결한 가장 낮은 버전. 동일 릴리스 브랜치를 우선하며, 동일 브랜치로 모두 해결할 수 없으면 그 브랜치의 최종 버전과 미해결 취약점을 표기한다(A안, FR-3) |
| 최신 버전 | 조회 시점 기준 알려진 취약점이 하나도 없는 가장 높은 안정(stable) 릴리스. 그런 버전이 없으면 가장 높은 안정 릴리스와 미해결 취약점을 표기한다 |
| 현재 집합 / 전체 집합 | 소스 버전에 영향을 주는 취약점 / 해당 컴포넌트의 알려진 전체 취약점 |

## 3. 입력 명세

### 3.1 파일
- 경로: `data/오픈소스_컴포넌트목록.xlsx`, 시트 `Sheet1`
- 열 구성

| 열 | 헤더 | 타입 | 비고 |
|---|---|---|---|
| A | No | int | 원본 목록의 일련번호(불연속: 1, 13, 14, 26 …). 그대로 보존한다 |
| B | 오픈소스 컴포넌트명 (Component name) | str | 헤더에 줄바꿈 포함 |
| C | 컴포넌트 버전 (Component version name) | str | 반드시 문자열로 읽는다(`1.7`, `8b` 등 숫자 변환 금지) |

### 3.3 입력 검증
- 필수 열이 없으면 오류 메시지를 내고 종료한다. 컴포넌트명/버전이 빈 행은 `INVALID_INPUT`으로 표시하고 나머지 행은 계속 처리한다.
- 매핑 파일에 없는 컴포넌트는 `UNMAPPED` 상태로 출력하고 로그에 남긴다(임의 추정 금지).

## 4. 기능 요구사항

### FR-1. 컴포넌트·버전별 취약점 식별
1. 각 행에 대해 3.2의 식별자로 취약점 DB를 조회한다.
2. 데이터 소스는 컴포넌트 유형에 따라 다음과 같이 조합한다.

| 유형 | 1차 소스 | 2차(교차검증) 소스 |
|---|---|---|
| Maven 패키지 | OSV.dev (`ecosystem=Maven`, GitHub Advisory 데이터 포함) | NVD (CVSS·설명 보완, CPE가 있으면 교차 확인) |
| C/C++ 네이티브 라이브러리 | NVD CVE API 2.0 (CPE 매칭, `virtualMatchString`) | 없음 — OSV는 C 라이브러리를 Git 커밋 범위 위주로 제공해 버전 판정에 부적합 |

   - GitHub Advisory API는 직접 조회하지 않는다(OSV에 포함, 토큰 불필요).
   - 조치 버전 판정을 위해 소스 버전에 해당하는 취약점만이 아니라 컴포넌트의 전체 취약점을 수집한다.

3. 소스 간 결과는 CVE ID 기준으로 병합하고 중복을 제거한다. GHSA/OSV ID만 있는 경우 alias의 CVE ID로 치환하며, CVE가 없으면 원 ID를 유지한다.
4. 버전 포함 여부 판정은 DB의 범위 정보(`versionStartIncluding`, `versionEndExcluding`, OSV `events`)를 기준으로 하며, 문자열 일치에 의존하지 않는다.
5. 거부(REJECTED) CVE는 항상 제외한다. 분쟁(DISPUTED) CVE는 기본 제외하고 `--include-disputed` 옵션으로 포함할 수 있게 한다.
6. 각 취약점에 대해 다음을 수집한다: CVE ID, 설명(영문 원문), CVSS 기본점수·심각도(v3.1 → v3.0 → v4.0 → v2 순), 영향 범위, 수정 버전(fixed), 근거 소스.

### FR-2. 조치 버전 탐색
1. 컴포넌트의 전체 릴리스 버전 목록을 확보한다.
   - Maven: Maven Central 메타데이터(`maven-metadata.xml`)
   - 네이티브: NVD CPE 사전(CPE API 2.0)의 버전 목록. NVD에 등록되지 않은 릴리스가 빠질 수 있는 한계는 감수한다
2. 소스 버전보다 높은 안정 버전(후보)마다 두 가지를 판정한다.
   - C-해결: 현재 집합의 어떤 취약점에도 영향받지 않는다
   - 무취약: 전체 집합의 어떤 취약점에도 영향받지 않는다
3. 판정 결과로 FR-3의 두 버전을 선택한다.

### FR-3. 조치 버전 표기 규칙
1. **해결 가까운 버전**
   - 1순위: 같은 릴리스 브랜치(예: OpenSSL 0.9.8x, zlib 1.2.x) 후보 중 C-해결인 가장 낮은 버전
   - 2순위: 1순위가 없으면(EOL 등) 같은 브랜치의 최종 버전을 제시하고 미해결 CVE와 `브랜치 변경 시` 권장 버전을 비고에 표기한다
   - 3순위: 소스 버전이 이미 브랜치 최종 버전이면, 다른 브랜치 후보 중 무취약인 가장 낮은 버전을 제시하고 `브랜치 변경`을 표기한다
   - 모두 없으면 `해결 버전 없음`
2. **최신 버전**: 무취약인 가장 높은 안정 릴리스(pre-release, rc, beta 제외). 없으면 가장 높은 안정 릴리스와 미해결 취약점을 표기한다. LTS 브랜치가 따로 있으면 비고에 LTS 버전을 함께 적는다.
3. 버전 비교는 생태계별 규칙을 따른다.
   - Maven: Maven ComparableVersion 규칙
   - OpenSSL 3.0 미만: 숫자 + 문자 접미사(`0.9.8h` < `0.9.8za` < `0.9.8zh` < `1.0.2u` < `1.1.1w`), 브랜치는 접미사를 뗀 숫자부
   - libjpeg: `8` < `8a` < `8b` < `8c` < `8d` < `9` …
   - LLVM: `llvmorg-` 접두사 제거, rc는 정식 버전보다 낮게 취급
4. 표기 예시(원본 요구사항 기준)
   ```
   소스 버전       : OpenSSL 0.9.8h
   해결 가까운 버전 : OpenSSL 0.9.8zh
   최신 버전       : OpenSSL 3.0.8   (예시 작성 시점 기준, 실제 값은 조회일에 따라 달라진다)
   ```

### FR-4. 결과 산출
4장 결과를 5장 형식의 엑셀로 저장한다. 실행은 두 단계로 나눈다: 인터넷 PC의 `collect`가 원천 응답을 묶음 파일(zip)로 저장하고, 폐쇄망 PC의 `scan`이 네트워크 없이 묶음만으로 분석한다. 실행 로그를 함께 남긴다.

## 5. 출력 명세

- 경로: `output/오픈소스_컴포넌트별 취약점목록_YYYYMMDD_HHMM.xlsx` (원본 템플릿 `data/오픈소스_컴포넌트별 취약점목록.xlsx`의 열 순서를 유지하고 오른쪽에 열을 추가한다)
- 행 단위: **CVE 1건당 1행**. 취약점이 없는 컴포넌트도 1행으로 남기고 `보안취약점 ID`에 `취약점 없음`을 기재한다.
- 정렬: 입력 No 오름차순 → CVSS 점수 내림차순

| # | 열 이름 | 출처 | 예시 |
|---|---|---|---|
| 1 | No | 입력 | 52 |
| 2 | 오픈소스 컴포넌트명 (Component name) | 입력 | OpenSSL |
| 3 | 컴포넌트 버전 (Component version name) | 입력 | 0.9.8h |
| 4 | 보안취약점 ID (Vulnerability id) | FR-1 | CVE-2014-0160 형식 |
| 5 | 보안취약점 설명 (Description) | FR-1 | 영문 원문 |
| 6 | CVSS 점수 | FR-1 | 7.5 |
| 7 | 심각도 | FR-1 | HIGH |
| 8 | 영향 버전 범위 | FR-1 | `>=0.9.8, <0.9.8za` |
| 9 | 해결 가까운 버전 | FR-3 | 0.9.8zh |
| 10 | 최신 버전 | FR-3 | (조회일 기준) |
| 11 | 비고 | FR-3 | 브랜치 변경 / 동일 브랜치 미해결 CVE / LTS 버전 |
| 12 | 근거 소스 | FR-1 | NVD; OSV |
| 13 | 조회일시 | 시스템 | 2026-10-10T14:00+09:00 |

- 해결 가까운 버전과 최신 버전은 컴포넌트 단위로 계산된 값이므로 같은 컴포넌트의 모든 행에 동일하게 기재한다. 요약 시트는 추가하지 않는다.
- 취약점 ID 열에는 취약점이 없는 행의 상태(`취약점 없음`, `UNMAPPED`, `UNCOLLECTED`, `INVALID_INPUT`)를 적는다.

## 7. 수용 기준(Acceptance Criteria)

1. 입력 13행이 모두 출력에 1행 이상 존재한다.
2. 취약점이 식별된 모든 컴포넌트에 `해결 가까운 버전`과 `최신 버전`이 채워지거나, 채울 수 없는 사유가 비고에 기재된다.
3. 표본 컴포넌트(OpenSSL, zlib 등 2~3개)의 결과를 NVD/OSV 웹 조회 결과와 수동 대조했을 때 누락·오탐이 없다.
4. OpenSSL 0.9.8h에 대해 해결 가까운 버전이 0.9.8 브랜치 버전(예상 0.9.8zh, 미해결 CVE 비고 포함)으로, 최신 버전이 무취약 최신 안정 버전과 LTS 비고로 표기된다.
5. 같은 묶음으로 `scan`을 다시 실행하면 출력이 동일하다(조회일시 열 제외). `scan`은 네트워크를 끈 상태에서도 정상 종료한다.
6. 단위 테스트 전부 통과.

## 8. 범위 외(Out of Scope)

- 실제 소스코드·바이너리 스캔을 통한 컴포넌트 자동 식별(입력은 이미 식별된 목록으로 가정)
- 취약점 도달 가능성(reachability) 분석, 익스플로잇 여부 판정
- 업그레이드 시 API 호환성(breaking change) 검증
- 라이선스 분석
- 도구 성능 평가·비교 실험
- GitHub Advisory API 직접 조회, NVD·OSV 전체 덤프 기반 로컬 DB, GUI
